# Perun ORM — дизайн v0.1 (скелет) — РАБОЧИЙ ДРАФТ

> Статус: рабочий черновик, зафиксированный из обсуждения дизайна. Не финал.
> Prose — RU, код/идентификаторы — EN. Переименовать/перенести свободно.

## 0. Цель и рамки

ORM на Swift 6 в семействе **Perun**. Два концептуальных слоя — **DBAL** и **ORM** — в **одном** репозитории, но **разными SPM-таргетами** (Doctrine-style split; DBAL пригоден отдельно). Стоит на двух уже написанных standalone-драйверах:

- **perun-pgsql** — PostgreSQL wire-протокол v3 с нуля, без SwiftNIO, OpenSSL только для TLS.
- **perun-sqlite** — обёртка над системным libsqlite3, API намеренно зеркалит pgsql.

Цель 0.1 — **крепкий скелет, доказывающий работоспособность слоя абстракции на ДВУХ бэкендах** (shared conformance-тест, который оба адаптера обязаны пройти). Осознанно **без** lazy-load, реляций и внешнего/second-level cache; обязательный session identity map остаётся частью UoW-семантики. ORM — «без дна»; 0.1 фиксирует швы, а не фичи.

## 1. Семейство Perun и слоистость (инверсия зависимости)

Зависимость инвертирована на границе драйвера: **ядро объявляет порт, адаптер реализует поверх конкретного драйвера**.

```
   PerunORM              сущности · маппинг · session/UoW · query-фасад
      │ импортит ядро
      ▼
   PerunDBAL — ЯДРО      объявляет порты: SQLExecutor / Transaction / Database / Row / ExecResult
      ▲                  + SQLValue · SQLDialect · SQL-AST · QueryBuilder+ParamBinder · SQLValueConvertible
      │ реализует порт   зависит НИ ОТ ЧЕГО нашего; слов «Postgres»/«SQLite» не знает
   PerunDBAL·Postgres — АДАПТЕР (МЕМБРАНА)
      │ импортит         импортит ЯДРО + драйвер; здесь и ТОЛЬКО здесь native-типы существуют
      ▼
   perun-pgsql — ДРАЙВЕР позиционный SQL + [PostgresEncodable] → native result
                        зависит только от C-libs · ни одной стрелки к нашему коду
```

Ядро не импортит адаптер — их сводит вместе только композиционный корень приложения (берёт ORM + ядро + выбранный адаптер, инъектит собранный `Database` в сессию). `Database` — логический фасад над пулом/клиентом, а не обещание одной физической connection. Его lifecycle тоже принадлежит композиционному корню: тот вызывает `Database.shutdown()` после завершения всех сессий; `Session` не закрывает инъектированную базу.

Таргеты 0.1: `PerunDBAL` (ядро) · `PerunDBALPostgres` / `PerunDBALSQLite` (адаптеры) · `PerunORM`. Отдельный macro-таргет (SwiftSyntax) для `@Model` появится только вместе с самим макросом после 0.1, чтобы базовый пакет пока не платил стоимость неиспользуемой зависимости.

## 2. Граница драйвера (жёсткое правило)

Драйверы **ничего не знают** о DBAL/ORM. Контракт границы — ровно два пункта:

- **Вход:** готовая SQL-строка с нативными плейсхолдерами (`$1` / `?`) + упорядоченный `[native encodable]`.
- **Выход:** нативный результат (native cells, `commandTag` / `rowsAffected` / `lastInsertRowID`).

Держится **графом пакетов, а не дисциплиной**: у драйвера в `Package.swift` нет и не может быть зависимости на Perun DBAL/ORM → нарушение = ошибка компиляции.

Анти-паттерны (никогда): ретрофитить нейтральный протокол/`SQLValue` в драйвер; протекать native-типами (`PostgresCell`) вверх через нейтральный `Row`. Нейтральность производится целиком в адаптере, двусторонне.

## 3. Два драйвера: поверхность и 4 шва

Драйверы — намеренные близнецы (тот же `*Client`-пул `init(config, maxConnections, maxConnectionLifetime, maxIdleTime)`, тот же `withTransaction { tx in }`, тот же `decode(col, as: T)` через свой `*Decodable`, bind `[(any *Encodable)?]`). Поэтому адаптеры почти одинаковы. Расходятся — вот здесь (это и есть работа DBAL):

| Аспект | perun-pgsql | perun-sqlite | Шов |
|---|---|---|---|
| Плейсхолдер | `$1, $2` | `?` | `Dialect.placeholder(i)` |
| Значение | сырые байты + OID + text/binary, decode on demand | `SQLiteValue` enum (5 storage-классов), типизировано сразу | bind — семантический `SQLValue`; read — по целевому типу |
| Affected / ключи | `commandTag` («INSERT 0 1»), нет last-insert-id | `rowsAffected` + `lastInsertRowID` полями | `ExecResult` нормализует affected и несёт rowid-hint без объявления его PK; основной путь ключей — RETURNING |
| Config | host/port/user/tls | path/journalMode/URI | единого config в ядре нет |
| Суперсилы | COPY, pipeline, LISTEN/NOTIFY, stream | backup, functions, hooks | escape hatch, не абстрагировать |

**Ключевой шов значения (bind vs read):**
- **Bind (параметры) → семантический нейтральный `SQLValue`** (`.bool/.date/.uuid/.int/…`); timestamp внутри `.date` уже представлен lossless `Int64`-микросекундами, а адаптер опускает их в native encodable по-своему (диалект-решение «как хранить Date» не течёт в ORM).
- **Read (результат) → target-type-driven `row.decode(col, as: T)`**; нейтральный `Row.decode` идёт через `SQLValue` (граница не пускает `PostgresDecodable` в протокол). Для 8 портабельных типов задан строгий канонический round-trip с явными range/precision rules; Date нормализуется до общей микросекундной точности. Богатые типы (jsonb/массивы) — через escape hatch.

PostgreSQL-адаптер включает binary parameter mode, чтобы driver передал type OID каждого значения в `Parse`; параметры с binary-представлением отправляются без text round-trip. Один `.int(Int64)` намеренно обслуживает и schema-тип `.int32`, и `.int64`, поэтому integer-wrapper передаёт OID `0` и не предоставляет binary-представление: driver отправляет именно этот параметр как text, а PostgreSQL выводит конкретную ширину из контекста statement вместо преждевременного `int8`. В raw SQL у целочисленного параметра без контекста (например, одинокого `SELECT $1`) caller обязан задать cast `::integer`/`::bigint`; сгенерированные INSERT/UPDATE/predicate уже дают контекст колонкой. Результаты запрашиваются в binary format и проверяются по OID; `timestamptz` декодируется напрямую из PostgreSQL-epoch `Int64`-микросекунд. Для bind собственный `PostgresTimestampParameter` кодирует те же микросекунды точно, без промежуточного `Date`.

## 4. Мембрана DBAL: SQLValue, Row, ExecResult

```swift
public struct SQLTimestamp: Sendable, Hashable {
    public let microsecondsSinceUnixEpoch: Int64?      // nil = non-finite/out-of-range error-state
}
public enum SQLValue: Sendable, Hashable {            // семантический носитель (bind) + нейтральная ячейка
    case null
    case bool(Bool), int(Int64), double(Double)
    case text(String), blob([UInt8]), date(SQLTimestamp), uuid(UUID)
}
public protocol Row: Sendable {                        // адаптер оборачивает PostgresRow / SQLiteRow
    func decode<T: SQLValueConvertible>(_ column: String, as: T.Type) throws -> T
    func decodeIfPresent<T: SQLValueConvertible>(_ column: String, as: T.Type) throws -> T?
}
public struct ExecResult: Sendable {
    public let rows: [any Row]                         // SELECT / RETURNING; порядок сохраняется
    public let rowsAffected: Int?                      // nil, если backend надёжно не сообщает
    public let lastInsertRowID: Int64?                 // SQLite hint; НЕ объявляется semantic/generated PK
}
public enum ExecutionIntent: Sendable {
    case arbitrary                                    // адаптер не угадывает семантику SQL
    case generatedRowIDInsert                         // caller доказывает generated INTEGER rowid
}
public protocol SQLExecutor: Sendable {
    func execute(_ sql: String, _ params: [SQLValue], intent: ExecutionIntent) async throws -> ExecResult
}
public protocol Transaction: SQLExecutor {}            // намеренно без withTransaction: nesting в 0.1 запрещён
public protocol Database: SQLExecutor {
    var dialect: any SQLDialect { get }                 // соединение и диалект невозможно рассинхронизировать
    func withTransaction<T: Sendable>(_ body: @Sendable (any Transaction) async throws -> T) async throws -> T
    func shutdown() async                               // lifecycle порта, вызывается composition root
}
```

Инварианты `ExecResult`: `rows` содержит только фактический result set; адаптер не парсит сырой SQL и не угадывает, какая колонка является PK. Обычная перегрузка `execute(sql, params)` передаёт `.arbitrary`, поэтому backend-specific hint остаётся `nil` даже для одиночного INSERT в `WITHOUT ROWID`. `lastInsertRowID` публикуется только для явного `.generatedRowIDInsert`, пустого result set и `rowsAffected == 1`; этим intent caller доказывает, что validated схема и сгенерированный SQL действительно используют автоматически назначенный generated `INTEGER PRIMARY KEY`/rowid alias. При `RETURNING` ORM гидрирует ключ из `rows`. Для DML `rowsAffected == 0` — нормальное достоверное значение, а не `nil`.

Две разные конверсии, не путать: `Swift-тип ↔ SQLValue` (`SQLValueConvertible`, ядро) и `SQLValue ↔ PostgresEncodable` (адаптер).

Транзакции — **closure-scoped** (снято с драйвера): `withTransaction { tx in }`, без open/commit-хендлов. Адаптер инвалидирует выданный `Transaction` после выхода из closure; попытка использовать утёкший handle обязана завершиться контролируемой ошибкой. `TransactionOptions` (SQLite `kind` locks vs PG isolation levels — разный смысл, не унифицировать) — в 0.1 только дефолт.

## 5. Диалект

**Чистый рендерер над AST** живёт в ядре. Не исполняет, не декодит, не есть AST. В `PerunDBAL` находятся `SQLDialect`, renderer и shared-дефолты стандартного SQL; конкретные `PostgresDialect` / `SQLiteDialect` живут в соответствующих адаптер-таргетах как stateless `Sendable` values. Поэтому ядро не знает имён backend'ов, а `Database.dialect` гарантирует, что исполнитель нельзя случайно соединить с чужим диалектом. Концерны: quoting (`placeholder`, `quoteIdentifier`), capabilities (feature-флаги), types (DDL), dml (limit/offset, returning, upsert), ddl (колонки/констрейнты, identity-фраза). Рендер потенциально невалидного публичного AST — throwing.

Три самых злых расхождения:
1. **Identity-PK — не «тип», а целая фраза колонки.** PG: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. SQLite: **ровно** `id INTEGER PRIMARY KEY` (ловушка: `BIGINT PRIMARY KEY` — обычная колонка, НЕ автоинкрементит). Метод `renderGeneratedPrimaryKeyColumn(_:) -> String` принимает имя и возвращает всю backend-specific фразу, включая quoting и PK.
2. **Дата/время — семантический разрыв.** У SQLite типа даты нет. На DBAL-границе `.date` несёт `SQLTimestamp` — точный `Int64` микросекунд от Unix epoch; `Date` не используется как semantic carrier, потому что повторное Double-округление неидемпотентно. `Date → SQLTimestamp` считает микросекунды относительно Foundation reference epoch и добавляет целочисленный epoch-offset; обратная конверсия ищет точное представимое `Date` и иначе бросает typed error. PostgreSQL-адаптер целочисленно переводит Unix epoch в PostgreSQL epoch для точного binary bind/read. SQLite-адаптер переводит integer timestamp в UTC proleptic Gregorian/POSIX и фиксированную RFC3339-форму `yyyy-MM-dd'T'HH:mm:ss.SSSSSS'Z'` только целочисленной арифметикой. UUID в SQLite — canonical lowercase hyphenated string из 36 символов.
3. **Типы непортабельны** → слой capability (`supportsReturning/Arrays/NativeUUID/…`), а не молчаливая эмуляция.

Генерируемые ключи: если `supportsReturning`, ORM делает `INSERT … RETURNING <all mapped columns>` и гидрирует строку. SQLite-адаптер 0.1 пока консервативно не заявляет `supportsReturning`, пока драйвер не экспонирует runtime version (`RETURNING` требует SQLite ≥ 3.35). Без `RETURNING` разрешён только явно заявленный capability fallback: одиночный INSERT, сгенерированный ORM для validated generated `.int64`/`INTEGER PRIMARY KEY`, выполняется с `.generatedRowIDInsert`, требует `rowsAffected == 1`, берёт `ExecResult.lastInsertRowID`, затем делает `SELECT` по нему **в той же транзакции**. Иначе операция завершается `unsupportedCapability`, а не угадывает ключ.

## 6. Портабельное ядро типов (`ColumnType`)

Закрытый нейтральный словарь схемы. Восемь типов на 0.1:

| `ColumnType` | Swift | PostgreSQL | SQLite | `SQLValue` |
|---|---|---|---|---|
| `.boolean` | `Bool` | `boolean` | `BOOLEAN` (storage INTEGER 0/1) | `.bool` |
| `.int32` | `Int32` | `integer` | `INT` | `.int` |
| `.int64` | `Int`, `Int64` | `bigint` | `BIGINT` | `.int` |
| `.double` | `Double`, `Float` | `double precision` | `REAL` | `.double` |
| `.text` | `String` | `text` | `TEXT` | `.text` |
| `.blob` | `[UInt8]`, `Data` | `bytea` | `BLOB` | `.blob` |
| `.timestamp` | `Date` | `timestamptz` | `TEXT` (ISO8601 UTC) | `.date(SQLTimestamp)` |
| `.uuid` | `UUID` | `uuid` | `TEXT`(36) | `.uuid` |

**Ортогональность** (в `ColumnType` НЕ входит): nullability = атрибут колонки (Swift `Optional`, выводится); identity/PK/generated = **роль** колонки. Enum(rawValue) → ложится на `.text`/`.int*`, не новый тип.

**Исключения (резерв, backend-specific, не 0.1):** `.decimal` (SQLite REAL ломает точность → только с конвенцией TEXT+`Decimal`-кодек), `.json`, `.array(T)` (PG-only).

**Когерентность:** `ColumnType` (схема) и `SQLValue` (значение) — две грани одного словаря. Новый тип = case в `SQLValue` + DDL в оба диалекта + lowering в оба адаптера + decode целевого типа. Пропустил пункт → тип полу-рабочий. Поэтому ядро маленькое.

**Decode строгий, без тихой потери данных:** SQLite boolean принимает только INTEGER `0/1`; `Int32` проверяет диапазон; finite Double→Float проверяет диапазон, а IEEE `±infinity`/`NaN` сохраняются симметрично на границе Swift↔`SQLValue`; UUID и timestamp обязаны соответствовать канону выше. Перед lowering каждый адаптер вызывает общую `SQLValue.validateForPortableBinding()`: `NaN`, non-finite и timestamp вне общего portable-диапазона `0001-01-01T00:00:00.000000Z ... 9999-12-31T23:59:59.999999Z` отклоняются одинаковой DBAL-ошибкой до драйвера, `±infinity` для `.double` разрешён обоими backend'ами. Timestamp round-trip сравнивает lossless `SQLTimestamp`; преобразование в `Date` разрешено только если точное обратное кодирование даёт те же микросекунды. Несовпадение storage class, переполнение и потеря обязательной точности — typed decode error.

## 7. Именованные параметры (решение)

**Сахар уровня DBAL, не фундамент. Перед ORM не нужны.** В wire-протоколе PG именованных нет (`$1` позиционные); эмуляция = security-sensitive токенайзер SQL → в драйвер не тащить, драйверы держать позиционными и симметричными. Правильный дом — один rewriter в DBAL над позиционным примитивом; примитив `execute(sql, [SQLValue])` остаётся позиционным, named — перегрузка-надстройка. Добавляется без rework в любой момент.

Фундаментально-рядом (делать сейчас): **`ParamBinder`-аккумулятор** в билдере (`emit(SQLValue) -> "$n"/"?"`, копит `[SQLValue]`) — делает склейку фрагментов безопасной без ручной нумерации. Живёт в ядре DBAL, драйвер его не видит.

## 8. Дескриптор сущности (маппинг)

Один дескриптор кормит **шесть** потребителей: DDL · INSERT/UPDATE/DELETE · SELECT+гидрация · dirty-diff · identity · резолв колонок в запросах.

Struct-решение: **гидрация через `init(row:)`** (структуру нельзя строить по частям), всё прочее — через KeyPath-мост. Nullability выводится из `Optional`.

```swift
// DBAL core: нейтральный мост Swift-значения (НЕ протокол драйвера)
public protocol SQLValueConvertible: Sendable {
    static var columnType: ColumnType { get }
    var sqlValue: SQLValue { get }
    init(sqlValue: SQLValue) throws
}
// Int/Int32/Int64/Double/String/Bool/[UInt8]/Data/Date/UUID + Optional<Wrapped> conform.

// ORM: маппинг одного поля
public enum ColumnRole: Sendable { case attribute, primaryKey(generated: Bool) }  // +.generated позже
public struct FieldDescriptor<Root: Sendable> {       // намеренно НЕ Sendable: Swift KeyPath не Sendable
    public let column: String
    public let type: ColumnType
    public let isNullable: Bool
    public let isUnique: Bool
    public let role: ColumnRole
    let keyPath: PartialKeyPath<Root>     // → резолв колонок для запросов
    let read: (Root) -> SQLValue           // → bind / dehydrate / dirty-diff
}

// ORM: контракт сущности (пишется руками; @Model генерит это же)
public protocol Entity: Sendable {
    associatedtype PK: SQLValueConvertible & Hashable
    static var tableName: String { get }
    static var fields: [FieldDescriptor<Self>] { get }
    init(row: Row) throws
    static func field(for keyPath: PartialKeyPath<Self>) -> FieldDescriptor<Self>  // из fields
}
```

PK — не второй источник metadata: ORM один раз строит и кэширует validated schema из `fields`, находит там ровно один `.primaryKey` и проверяет, что его `ColumnType` совпадает с `PK.columnType`. До первого SQL валидируются: непустые и уникальные без учёта регистра имена колонок (portable SQLite rule); каждый KeyPath объявлен ровно один раз; ровно один non-null PK, причём и поле, и `Entity.PK` не Optional; PK присутствует в `fields`; generated PK в 0.1 только `.int64`; обычный PK только со стабильной identity-семантикой (`boolean/int32/int64/text/blob/uuid`, не `double/timestamp`); непротиворечивость `type`/`isNullable` с KeyPath. Изменение PK у managed entity через `update` запрещено. `isUnique` покрывает column-level UNIQUE в 0.1; table-level/composite constraints отложены.

`Optional<Wrapped>` участвует как значение поля, но runtime schema validation запрещает его в `Entity.PK`. Entity обязана иметь value semantics: reference-type Entity отклоняется как `referenceTypeUnsupported`, а напрямую mapped reference-typed поле (включая обёртку `Optional`) — как `referenceFieldTypeUnsupported`, потому что возвращённый наружу mutable объект мог бы одновременно изменить snapshot внутри identity map и превратить dirty-diff в ложный no-op. Проверка типа поля не доказывает глубокую value-semantic структуру пользовательского типа, поэтому ORM дополнительно замораживает mapped `[SQLValue]` в момент принятия каждого managed snapshot и вообще не сохраняет caller-visible Entity в identity map или overlay. Compile-spike на Swift 6.3 подтвердил: `KeyPath`/`PartialKeyPath` не `Sendable`. Поэтому `FieldDescriptor` намеренно остаётся синхронным non-Sendable mapping-объектом, создаётся computed metadata и при необходимости кэшируется только в actor-isolated состоянии ORM. Query-фасад резолвит KeyPath в имя колонки **до** async/task-границы; дальше движутся только Sendable SQL-узлы/значения. `Entity` и реальные данные остаются `Sendable`; `@unchecked Sendable` для mapping не используется.

После 0.1 `@Model` станет member-macro поверх stored properties + маркеры (`@PrimaryKey`, `@Column`), генерирующим ровно ручную форму (протокол — истина, макрос — сахар). Naming strategy по умолчанию: `camelCase` → `snake_case`.

## 9. Session и Unit of Work

Lifecycle фиксирован явно: `Database`/pool живёт на уровне приложения, `Session` — одного request
или command, `UnitOfWork` — только своей closure. Session-local identity map не переносится между
независимыми запросами; validated-schema cache пока разделяет тот же lifecycle и строится заново
для новой Session. Закрытый escaped `UnitOfWork` освобождает ссылки на transaction и Session, а не
только отклоняет последующие вызовы.

**Managed для value-type Entity = снапшот по `(ObjectIdentifier(type), pk: SQLValue)`.** Мутации локальной копии сессии невидимы; попадают в её мир через `update(entity, from: snapshot)`, где `snapshot` — последнее значение, возвращённое `find`/`insert`/`update`. Identity map и UoW overlay не удерживают caller-visible Entity: managed snapshot состоит только из type marker, PK и immutable mapped `[SQLValue]`. Каждый cache hit материализует новую Entity через `init(row:)` из внутренней typed frozen row, поэтому даже скрытый reference-backed computed field не может задним числом переписать managed-базу или следующий результат `find`. `find` возвращает detached snapshot, **не** несабмиченные локальные правки.

**Closure-драйвер ⇒ closure-UoW:** `session.withUnitOfWork { uow in … }` оборачивает `database.withTransaction { tx in … }`. Конкретный `UnitOfWork` владеет полученным `Transaction`; `Session` никогда не хранит `currentTx`. Так actor reentrancy не может случайно направить посторонний вызов в чужую транзакцию. На закрытии UoW сначала запрещает новые операции, затем ждёт все уже начатые in-flight вызовы и только после этого возвращает управление для COMMIT/ROLLBACK. Escaped handle при дальнейшем вызове бросает ошибку.

**0.1 = eager внутри closure** (не queue-then-flush): `insert` выполняет INSERT и сразу гидрирует сущность **с готовым id** через `RETURNING` либо описанный generated-key fallback. Атомарность есть. **Deferred-батч (`pipeline`) + FK-топосорт — это 0.2**, тот же API `withUnitOfWork`, меняется лишь тайминг.

**Корректность:** DB-запись eager (внутри tx), но UoW ведёт локальный overlay + change set. `insert`/`update` кладут новую сущность в overlay, `delete` — tombstone; последующие `uow.find` сначала смотрят туда, поэтому обеспечивается see-your-writes. Новые snapshots продвигаются в глобальный identity map только после успешного возврата `Database.withTransaction`, то есть подтверждённого commit. Консервативная eviction потенциально устаревших base snapshots может происходить раньше и намеренно сохраняется при body/commit error как безопасный cache miss; сам overlay при ошибке целиком отбрасывается. PG-sequence на rollback не откатывается — гэпы норма.

**Concurrency-policy 0.1:** `Session` — actor, но actor reentrant на `await`. Поэтому она считает прямые in-flight DB-операции и отдельно хранит active-UoW token: UoW не стартует, пока уже выполняется direct operation; после старта UoW новые прямые/nested/параллельные операции завершаются `sessionBusy`. Несколько direct operations могут пересекаться, поэтому identity map имеет monotonic revision: обычные `find/fetch` кэшируют результат только при неизменившейся revision, а raw unknown-effect operation сдвигает её до и после executor-вызова. Так старый read, начатый до raw SQL или во время него, может вернуть собственный результат caller'у, но не способен поздно восстановить уже инвалидированный snapshot. Внутри closure все операции идут только через переданный `uow`, строго по одной: второй вызов, пока первый suspended на драйвере, получает `unitOfWorkBusy`. После начала закрытия любой новый вызов получает `unitOfWorkClosed`, а уже начатый завершается до COMMIT/ROLLBACK. Любая ошибка `Transaction.execute` делает UoW rollback-only: новые операции получают `unitOfWorkRollbackOnly`, а `close()` заставляет transaction closure бросить ошибку, даже если исходный failure был перехвачен body или находился в возвращённом started `Task`. Для ORM-записей и raw hydration то же правило действует после успешного executor-вызова, если не прошли проверка результата или гидрация. Ошибки schema/render/capability до executor-вызова остаются recoverable. Transaction-control (`BEGIN`/`COMMIT`/`ROLLBACK`/savepoint-команды и стандартные синонимы) через raw `uow.execute` и `uow.fetch(E.self, sql:)` отклоняется до драйвера и сразу переводит UoW в rollback-only, поэтому raw hatch не может разорвать closure-транзакцию. Это простая детерминированная политика; очередь/async mutex можно добавить позже без смены публичной модели.

Операции: `find` (overlay→base snapshot→SELECT→`init(row:)`→overlay); `insert` (PK с `generated:true` не биндим); `update` (требует последний managed snapshot: изменённый PK → `primaryKeyChanged`, устаревшая база → `staleEntitySnapshot`, отсутствующая identity → `entityNotManaged`; dirty mapped columns; пусто→no-op; явный blind full UPDATE отложен); `delete` (по PK → tombstone). Для UPDATE/DELETE `rowsAffected == 0` означает `entityNotFound`, `>1` для одноколоночного PK — нарушение инварианта. Если backend возвращает `nil`, операция разрешена, но точную проверку существования гарантировать нельзя; это отражает capability.

Первый read-slice реализует прямой `Session.find(E.self, pk)`: один раз validated и actor-кэшированный `EntitySchema` строит internal DDL/SELECT AST bridge, но сессия сама не создаёт и не мигрирует таблицы. До обращения к БД проверяется identity map по `(ObjectIdentifier(E.self), pk.sqlValue)`; cache hit возвращает сохранённый snapshot. Cache miss выполняет SELECT всех mapped columns по PK с `LIMIT 2`, возвращает `nil` для пустого результата, отклоняет несколько строк и несовпадение гидрированного PK с запрошенным, затем кэширует `E.init(row:)`. Операция участвует в общем direct-operation guard и не может пересечь active UoW.

Первый write-slice добавляет eager `UnitOfWork.insert(entity) -> E` и transactional `uow.find`. UoW получает от своей `Session` token-authenticated планы из того же actor-кэшированного `EntitySchema`, а сам хранит только Sendable SQL и локальный overlay. INSERT сохраняет порядок mapped fields и исключает generated PK; dialect с `returning` запрашивает все mapped columns и гидрирует итоговую сущность. Без `RETURNING` обычный PK возвращает входной snapshot, а generated `.int64` разрешён только при `lastInsertRowID`: INSERT выполняется с `.generatedRowIDInsert`, требует `rowsAffected == 1` и rowid, затем строка читается через тот же PK SELECT внутри той же транзакции. `uow.find` проверяет overlay, потом базовый session snapshot и только затем transaction SELECT, поэтому insert виден немедленно. При выходе UoW закрывается и отдаёт Sendable snapshots как transaction outcome; `Session` сливает их в identity map только после успешного возврата `Database.withTransaction`. Body/commit error полностью отбрасывает overlay. Общий executor wrapper помечает UoW rollback-only при любой ошибке transaction executor, а INSERT дополнительно делает это при ошибке проверки или гидрации после успешной записи; такую ошибку нельзя поглотить и случайно продвинуть overlay после фактического rollback на backend. После успешной подготовки inserted snapshot его точный ключ немедленно эвиктится из session identity, поэтому неизвестный commit outcome не оставляет прежнюю сущность под тем же PK; rollback в худшем случае приводит к cache miss. Успешный raw `uow.execute` имеет неизвестный read/write effect, поэтому консервативно очищает накопленный overlay, отключает base-cache hits для следующих ORM-чтений и немедленно инвалидирует session identity целиком. Ранняя инвалидация намеренно сохраняется даже при rollback: безопасный cache miss предпочтительнее stale snapshot при ошибке или отмене после уже завершившегося COMMIT. После успешного commit в identity продвигаются только заново полученные snapshots; правило действует и для фактически read-only raw SQL. Direct `Session.execute` находится вне rollback boundary, поэтому инвалидирует identity до и после любого executor outcome; это намеренно консервативнее transactional пути.

Второй write-slice добавляет managed-only `UnitOfWork.update(entity, from: snapshot) -> E`. Явный исходный snapshot сохраняет identity value-type сущности: его PK должен совпадать с PK нового значения, а все mapped значения — с замороженной базой последнего snapshot того же ключа в overlay либо session identity. Поэтому смена PK отклоняется как `primaryKeyChanged` даже при уже managed новом ключе, повторное использование старой базы — как `staleEntitySnapshot`, а отсутствующая identity — как `entityNotManaged`; все три pre-write ошибки recoverable. `EntitySchema` сравнивает mapped `SQLValue` в порядке объявления полей, считает два IEEE `NaN` одним неизменившимся snapshot-значением, никогда не включает PK в `SET` и возвращает no-op при пустом diff. Диалект с `returning` запрашивает все mapped columns, гидрирует результат и повторно проверяет PK; без `RETURNING` новым snapshot становится входная сущность. Известный `rowsAffected == 0` даёт `entityNotFound`, значение больше одного — `unexpectedUpdateAffectedRowCount`, а `nil` принимается как отсутствие точной backend-гарантии. После завершившегося UPDATE прежний base snapshot этого ключа немедленно эвиктится, новая сущность видна через overlay и продвигается в Session только после commit. Ошибка affected-row проверки, `RETURNING` или гидрации после executor-вызова переводит UoW в rollback-only; неизвестный commit outcome оставляет безопасный cache miss, а не потенциально устаревший snapshot.

Третий write-slice добавляет managed-only `UnitOfWork.delete(snapshot)`. Перед SQL переданный value-type snapshot сверяется со всеми замороженными mapped значениями последнего snapshot того же ключа в overlay либо session identity: detached значение даёт `entityNotManaged`, устаревшее — `staleEntitySnapshot`, а повторное удаление tombstone отклоняется до executor-вызова. DELETE строится тем же validated `EntitySchema` по PK. После успешного executor-вызова точный ключ немедленно эвиктится из session identity, а локальный tombstone делает последующий `uow.find` равным `nil`; INSERT того же PK может заменить tombstone новым snapshot. Известный `rowsAffected == 0` даёт `entityNotFound`, значение больше одного — `unexpectedDeleteAffectedRowCount`, а `nil` принимается согласно backend capability. Ошибка проверки после записи переводит UoW в rollback-only. Commit продвигает tombstone как удаление ключа из identity map; body/commit error отбрасывает tombstone, сохраняя раннюю eviction как безопасный cache miss, поэтому rollback заново читает существующую строку из БД.

```swift
public actor Session {
    private let database: any Database

    private var activeUnitOfWork: UUID?                   // reentrancy guard, не transaction storage
    private var activeDatabaseOperations: Int = 0

}
public actor UnitOfWork {                                 // Sendable по actor-модели
    private let transaction: any Transaction
```

## 10. Query / predicate-строитель

Два слоя: **DBAL core — строковый predicate/SELECT-AST** (колонки-строки, значения `SQLValue`, операторы-enum, диалект рендерит через `ParamBinder`); **ORM — типизированный фасад** над KeyPath'ами, который **резолвит `\.age` → колонку в момент построения** и кладёт наружу ядровый строковый узел (generic-ность только на поверхности, в ядро не течёт).

DSL — **комбинаторы, не операторы** в 0.1 (`==` на KeyPath занят стдлибом; операторный сахар + `Column`-токены — macro-эра).

```swift
// DBAL core
public enum SQLPredicate: Sendable {
    case comparison(column: String, op: ComparisonOp, value: SQLValue)
    case inList(column: String, values: [SQLValue])
    case null(column: String, negated: Bool)
    indirect case and([SQLPredicate]); indirect case or([SQLPredicate]); indirect case not(SQLPredicate)
}
public enum ComparisonOp: Sendable { case eq, neq, lt, lte, gt, gte, like }
public struct SQLCount: Sendable {
    public static let resultColumn = "count"
    public let table: String
    public let predicate: SQLPredicate?
}

// ORM
public enum ORMQueryError: Error, Sendable {
    case unmappedField(entity: String)
}
public struct Predicate<E: Entity>: Sendable {
    let core: SQLPredicate
    public static func eq<V: SQLValueConvertible>(_ kp: KeyPath<E, V>, _ v: V) throws -> Predicate   // v==nil → IS NULL
    public static func neq<V: SQLValueConvertible>(_ kp: KeyPath<E, V>, _ v: V) throws -> Predicate
    public static func lt<V: SQLValueConvertible & Comparable>(_ kp: KeyPath<E, V>, _ v: V) throws -> Predicate
    public static func lte<V: SQLValueConvertible & Comparable>(_ kp: KeyPath<E, V>, _ v: V) throws -> Predicate
    public static func gt<V: SQLValueConvertible & Comparable>(_ kp: KeyPath<E, V>, _ v: V) throws -> Predicate
    public static func gte<V: SQLValueConvertible & Comparable>(_ kp: KeyPath<E, V>, _ v: V) throws -> Predicate
    public static func like(_ kp: KeyPath<E, String>, _ pattern: String) throws -> Predicate
    public static func isNull<V: SQLValueConvertible>(_ kp: KeyPath<E, V?>) throws -> Predicate
    public static func `in`<V: SQLValueConvertible>(_ kp: KeyPath<E, V>, _ vs: [V]) throws -> Predicate
    public func and(_ o: Predicate) -> Predicate; public func or(_ o: Predicate) -> Predicate; public func not() -> Predicate
}
public struct Query<E: Entity>: Sendable {
    let statement: SQLSelect
    public init(_ entity: E.Type = E.self) throws
    public func `where`(_ p: Predicate<E>) -> Query                 // последовательные → AND
    public func order<V>(by kp: KeyPath<E, V>, desc: Bool = false) throws -> Query
    public func limit(_ n: Int, offset: Int = 0) -> Query
}
public actor Session {
    public func fetch<E: Entity>(_ q: Query<E>) async throws -> [E]
    public func fetch<E: Entity>(_ type: E.Type, sql: String, params: [SQLValue] = []) async throws -> [E]
    public func first<E: Entity>(_ q: Query<E>) async throws -> E?
    public func count<E: Entity>(_ q: Query<E>) async throws -> Int64
}
```

Первый query-slice реализует immutable `Predicate<E>`/`Query<E>` без async state. Каждая фабрика predicate и `order(by:)` синхронно строит и валидирует `EntitySchema`, резолвит KeyPath в имя mapped-колонки и сохраняет только Sendable `SQLPredicate`/`SQLSelect`; unmapped KeyPath даёт `ORMQueryError.unmappedField`, а не trap. `eq`/`neq` принимают Optional и передают `.null` в core для корректного `IS NULL`/`IS NOT NULL`; ordered-комбинаторы статически ограничены `Comparable`, `like` — non-optional `String`, `isNull` — Optional mapped field, `in` сохраняет null-элементы для семантической переписи renderer'ом. Последовательные `where` и однотипные `and`/`or` объединяются в плоские списки с сохранением порядка, `order` накапливается, повторный `limit` заменяет пагинацию. `offset: 0` нормализуется в отсутствие OFFSET, чтобы обычный limit сохранял prefix-pagination путь диалектов; отрицательные значения остаются renderer error.

Корректность рендера: пустой `IN` → `FALSE` (переносимое `1 = 0`); `eq(.null)` / `neq(.null)` → `IS NULL` / `IS NOT NULL`; `.null` с `lt/lte/gt/gte/like` → render error. `IN` с null-элементами переписывается семантически: non-null список плюс `OR column IS NULL`; список только из null → `IS NULL`. Пустые `and`/`or` дают нейтральные `1 = 1` / `1 = 0`. Порядок параметров согласован по построению (`ParamBinder` в один проход); идентификаторы всегда квотятся диалектом; `LIKE`, limit и offset всегда параметры. Отрицательная пагинация отклоняется; portable 0.1 требует limit, если задан offset. Диалект возвращает throwing `SQLPaginationPlan` из literal/parameter-фрагментов, placement (`afterSelect` или `suffix`) и контекста наличия ordering; renderer связывает параметры в лексической точке вставки. Поэтому шов выражает и `TOP`, и требующий `ORDER BY` вариант `OFFSET … FETCH`, не ломая порядок placeholders. Core default использует стандартный `OFFSET … ROWS FETCH FIRST … ROWS ONLY`, а PostgreSQL/SQLite явно переопределяют grammar как `LIMIT … OFFSET …`; совпадение двух текущих backend'ов не возводится в инвариант.

`SQLInsert` — одиночный INSERT из упорядоченных column/value-пар; пустой список даёт `DEFAULT VALUES`, повтор колонки без учёта регистра отклоняется как непереносимый. `SQLUpdate` — однотабличный UPDATE с непустым упорядоченным `SET`; `SQLDelete` — однотабличный DELETE. У UPDATE/DELETE параметр `predicate` не имеет default, явный `nil` означает изменение всех строк. Значения всегда bind-параметры, для UPDATE сначала связывается `SET`, затем `WHERE`. Необязательный список `returning` валидируется как идентификаторы и требует `.returning`; диалект задаёт общий DML placement-план `embedded` или `suffix`, поэтому PostgreSQL `RETURNING` и SQL Server-like `OUTPUT INSERTED/DELETED` выражаются одним core AST без жёстко прошитой общей грамматики. SQLite 0.1 не заявляет capability и получает явный render error вместо неявного fallback.

`SQLCreateTable` — упорядоченный список backend-neutral `SQLColumnDefinition`. Core валидирует непустую таблицу и список колонок, имена без NUL, переносимую уникальность имён без учёта регистра, не более одного non-null PK и generated PK только типа `.int64`; затем сам собирает `NOT NULL`, обычный `PRIMARY KEY` и column-level `UNIQUE`. Диалект задаёт spelling всех восьми `ColumnType`, а generated PK получает как целую фразу через `renderGeneratedPrimaryKeyColumn(_:)`. Поэтому SQLite резервирует точное `INTEGER PRIMARY KEY` только для generated rowid alias, а обычные integer-like типы объявляет как `BOOLEAN`/`INT`/`BIGINT`; PostgreSQL использует identity-семантику. DDL не содержит bind-параметров.

Второй query-slice добавляет `session.fetch(query) -> [E]` и `uow.fetch(query) -> [E]`. Typed query всегда исполняет SELECT: identity map не может надёжно вычислить membership, ordering или pagination. Все строки сначала гидрируются во временный ordered batch, их PK извлекаются из тех же frozen mapped values, а повтор PK отклоняется как `multipleRowsForPrimaryKey`; только полностью успешный batch атомарно обновляет cache. Прямой `Session.fetch` применяет к возвращённым ключам 0.1 last-read-wins, не делая выводов о ключах, которых нет в результате. `UnitOfWork.fetch` исполняется через принадлежащий UoW transaction и кладёт batch в overlay, поэтому eager insert/update/delete видны запросу и последующим `uow.find`; promotion происходит только после commit, body/commit error отбрасывает read-overlay. Schema/render/hydration ошибки recoverable и не оставляют частичного batch, ошибка transaction executor по общей политике переводит UoW в rollback-only. Во время active UoW вызывается `uow.fetch`, а прямой `session.fetch` получает `sessionBusy`.

Третий query-slice завершает typed terminal API методами `session.first/count` и `uow.first/count`. `first` переиспользует путь `fetch`, сохраняя predicate, ordering и offset, но заменяя отсутствующий limit на 1 и ужимая существующий до `min(limit, 1)`; поэтому `limit(0)` остаётся пустой выборкой, а отрицательный limit продолжает давать render error. Успешная строка получает те же direct/UoW snapshot semantics, что и обычный fetch.

`count` возвращает `Int64` и строит отдельный минимальный `SQLCount(table, predicate)` как `COUNT(*) AS "count"`: ordering и pagination намеренно не представлены, поэтому считается полная membership после `WHERE`, а не текущая страница. Aggregate не гидрирует Entity и не меняет identity map/overlay, но transactional вариант видит все eager writes своего UoW. Результат обязан содержать ровно одну строку; неверная форма и decode error recoverable, тогда как ошибка transaction executor делает UoW rollback-only. Прямые `first/count` во время active UoW получают `sessionBusy`.

Четвёртый query-slice добавляет raw hydrating escape hatch `session.fetch(E.self, sql:, params:)` и `uow.fetch(...)`. Caller полностью владеет SQL и positional binds; ORM до executor-вызова валидирует `EntitySchema`, затем гидрирует все result rows тем же временным ordered batch и отклоняет duplicate PK. Полученные entities всегда остаются detached: raw statement имеет неизвестный read/write effect, а строка из `DELETE ... RETURNING` уже не является текущим snapshot. Direct `Session.fetch` поэтому сдвигает identity revision и очищает cache до и после executor-вызова даже при ошибке с неизвестным autocommit outcome, но не кэширует возвращённый batch. Обычные concurrent `find/fetch` с прежней revision возвращают прочитанные значения caller'у, но не кэшируют их.

Transactional raw fetch запрещает transaction-control тем же scanner'ом, что `uow.execute`. После успешного executor-вызова он очищает прежний overlay, отключает base-cache hits и немедленно инвалидирует session identity; возвращённый batch не попадает в новый overlay. Последующий managed snapshot можно получить обычным `uow.find` или typed `uow.fetch`. Schema error до execution recoverable; executor error и любая decode/duplicate-PK ошибка после execution переводят UoW в rollback-only, поскольку raw SQL мог быть DML с `RETURNING`. Body/commit failure не меняет detached-семантику результата, а ранняя eviction остаётся безопасным cache miss. Typed query fetch сохраняет прежнюю read-only recoverability и не получает эту более строгую raw-политику.

## 11. Скоуп v0.1

**In:**
- DBAL: `SQLExecutor`/`Transaction`/`Database`/`Row`/`ExecResult`; `SQLValue`/`SQLValueConvertible`; два адаптера (PG, SQLite) с нормализацией 4 швов; dialect protocol + concrete dialects в адаптерах (quoting/capabilities/types/limit-offset/returning); `ColumnType` (8 типов); `ParamBinder`; SQL-AST + throwing renderer; DDL `CREATE TABLE` (типы + PK/identity + NOT NULL + column UNIQUE).
- ORM: `Entity`/`FieldDescriptor` + validated schema; `Session` (actor) + identity-map-снапшоты; `withUnitOfWork` (closure=tx, eager, local overlay, busy guard); CRUD `find`/`insert`(RETURNING/fallback)/`update`(dirty-diff)/`delete`; post-commit bookkeeping; `Query`/`Predicate` (одно-табличный SELECT всех колонок, WHERE eq/neq/lt/lte/gt/gte/like/in/isNull + and/or/not, ORDER BY, LIMIT/OFFSET, count); raw-hatch.
- **Shared conformance** состоит из двух одинаково параметризованных suites: DBAL suite проверяет порт/типы/транзакции/рендер на обоих адаптерах; ORM behavior suite прогоняет одинаковые schema+CRUD+query+rollback сценарии через обе `Database`-фабрики. SQLite in-memory (`file::memory:?cache=shared` для пула) для CI, PG в контейнере. Это операционализирует «две БД доказывают слой».

**Отложено (слоты зарезервированы):** реляции/JOIN'ы (в SELECT-AST пустой `joins: []`, колонка → расширить до `(alias?, column)`); lazy-load (только явные holder'ы, не property-магия); deferred-батч flush + `pipeline` + FK-топосорт; savepoints/вложенные UoW (у драйвера нет → 0.1 nested всегда throws); каскады; lifecycle-хуки; составной PK; проекции/агрегаты сверх count; подзапросы; macro-таргет с `@Model` и операторный сахар (`\.age > 18`); миграции/интроспекция схемы; `.decimal`/`.json`/`.array`; named parameters; naming/detached-политики строже дефолта.

**Эргономика в бэклог:** `@Model` генерит `E.draft(...)` без generated-PK (чтобы не писать `id: 0`); `.contains`/`.startsWith` с экранированием LIKE; hardening SQLite-адаптера `SQLITE_DBCONFIG_DQS_DML/DDL = 0`.

## 12. Design guards и открытое

- **Не над-фитить под близнецов.** Два похожих бэкенда доказывают, что шов есть, но недосэмплируют расхождения. «Общие 80%» (LIMIT/OFFSET, `ON CONFLICT`) — совпадение PG+SQLite, не инвариант. Размерять швы под известные-более-злые: MySQL (нет RETURNING, `ON DUPLICATE KEY`, backticks), SQL Server (`TOP`/`OFFSET…FETCH`, `IDENTITY`, `OUTPUT`), Oracle (sequences, нет bool). Не-близнец-драйвер → **толстый адаптер по дизайну**, это его работа.
- Дефолты диалекта писать как «стандартный SQL / общий случай», совпадение PG+SQLite в фундамент не возводить.
- **Интеграционный graph guard:** auxiliary targets драйверов имеют глобально уникальные имена (`PerunPGSQL*` / `PerunSQLite*`); опубликованные `perun-pgsql 0.3.0` и `perun-sqlite 0.2.0` загружаются в один SwiftPM dependency graph. Library products/API драйверов при этом не меняются.
- **Shared DBAL conformance guard:** SQLite in-memory и gated live PostgreSQL выполняют одну матрицу: восемь portable-типов + NULL, bind rejection, strict decode, affected rows, commit и rollback. Context-free scalar round-trip без cast для нецелочисленных типов отдельно доказывает, что PostgreSQL adapter передал type OID в `Parse`; целые остаются OID `0` и требуют контекста statement по контракту выше. Backend-specific тесты отдельно покрывают PostgreSQL timestamp/command-tag codec и безопасную публикацию SQLite rowid hint.
- **SELECT renderer guard:** точные PostgreSQL/SQLite snapshots фиксируют quoting, grouping и порядок bind-параметров; contract-тест SQL Server-like диалекта фиксирует обе placement-ветки пагинации, лексический bind order и обязательный `ORDER BY` для `OFFSET … FETCH`; тот же AST с predicate, nullable `IN`, ordering и pagination выполняется в shared live matrix на обоих адаптерах.
- **COUNT renderer guard:** отдельный `SQLCount` фиксирует quoted result alias, table/predicate quoting и bind order на PostgreSQL/SQLite, структурно не умеет переносить ordering/pagination и переиспользует общую predicate validation.
- **INSERT renderer guard:** точные snapshots фиксируют PostgreSQL `RETURNING`, SQLite без него, `DEFAULT VALUES`, quoting и bind order; SQL Server-like contract фиксирует `OUTPUT` перед value source; shared live matrix на обоих адаптерах выполняет только сгенерированные INSERT statements, а capability-gated PostgreSQL ветка исполняет `RETURNING` и декодирует его result row.
- **UPDATE renderer guard:** точные snapshots фиксируют PostgreSQL/SQLite grammar, quoting и порядок `SET`→`WHERE` параметров; SQL Server-like contract фиксирует embedded `OUTPUT`; shared live matrix проверяет сгенерированные UPDATE и `rowsAffected == 0/1`, capability-gated PostgreSQL ветка исполняет `UPDATE … RETURNING`.
- **DELETE renderer guard:** точные snapshots фиксируют PostgreSQL/SQLite grammar, nullable `IN`, quoting и bind order; SQL Server-like contract фиксирует embedded `OUTPUT DELETED`; shared live matrix проверяет сгенерированные DELETE и `rowsAffected == 0/1`, capability-gated PostgreSQL ветка исполняет `DELETE … RETURNING`.
- **CREATE TABLE renderer guard:** точные PostgreSQL/SQLite snapshots фиксируют spelling всех восьми типов, quoting, `NOT NULL`, обычный/generated PK и column `UNIQUE`; structural tests отклоняют пустой/дублированный набор колонок, nullable/составной PK и generated PK не `.int64`. Shared live matrix создаёт обе схемы только через renderer, требует одинакового отказа INSERT без ordinary PK, затем вставляет строку без generated id и проверяет PostgreSQL `RETURNING` либо SQLite `.generatedRowIDInsert` с последующим SELECT.
- **ORM find guard:** unit-тесты фиксируют `EntitySchema → SQLCreateTable/SQLSelect`, quoting и bind order, schema validation до SQL, cache hit без второго execute, missing row, duplicate rows и PK mismatch без отравления identity map. Shared SQLite/live PostgreSQL behavior создаёт схему через тот же bridge и доказывает snapshot-семантику внешним UPDATE: текущая сессия возвращает кэш, новая видит свежую строку.
- **ORM insert guard:** unit-тесты фиксируют generated/assigned `EntitySchema → SQLInsert`, исключение generated PK, порядок bind/RETURNING, безопасный отказ без key-retrieval capability, SQLite rowid intent + SELECT в той же transaction, UoW see-your-writes и post-commit promotion. Body/commit failure не продвигает UoW overlay; swallowed post-write error, raw/SELECT executor error и failure в возвращённом started `Task` переводят UoW в rollback-only и не достигают commit, тогда как pre-write capability error остаётся recoverable. Успешный INSERT немедленно инвалидирует совпадающий base key даже при неизвестном commit outcome; успешный raw DML инвалидирует прежние overlay/base snapshots целиком, а замаскированный комментариями transaction-control отклоняется до executor и заставляет rollback. Shared SQLite/live PostgreSQL behavior выполняет generated insert через разные backend-пути, проверяет свежую сессию, реальный rollback, отсутствие phantom после raw DELETE и сохранность transaction boundary.
- **ORM update guard:** unit-тесты фиксируют value-type schema, frozen mapped baseline, detached materialization на каждом Session/UoW cache hit, explicit latest snapshot, managed lookup, mapped dirty-diff и порядок bind `SET`→PK, запрет PK в assignments, no-op без SQL, PostgreSQL `RETURNING`, SQLite snapshot path, повторный diff от последнего overlay и post-commit promotion. Reference Entity и reference-typed mapped field отклоняются схемой; скрытая reference-backed мутация не меняет managed-базу или следующий cached read, а неизменившийся `NaN` не попадает в dirty assignments. Смена PK при двух managed ключах, stale snapshot и detached identity отклоняются до write; `rowsAffected == 0/>1`, неверный result-row count и PK mismatch после write делают UoW rollback-only. Commit failure не продвигает overlay и оставляет точный base key инвалидированным. Shared SQLite/live PostgreSQL behavior проверяет одинаковые update, see-your-writes, no-op, commit и реальный rollback.
- **ORM delete guard:** unit-тесты фиксируют `EntitySchema → SQLDelete`, quoting и bind order, latest frozen snapshot, managed-only lookup, локальный tombstone, delete после update/insert, повторный insert того же PK и post-commit удаление identity. Detached/stale snapshot и повторный delete отклоняются до write; `rowsAffected == 0/>1` после write делают UoW rollback-only. Commit failure не продвигает tombstone и оставляет точный base key инвалидированным. Shared SQLite/live PostgreSQL behavior проверяет одинаковые DELETE, see-your-writes, commit, удаление из свежей сессии и реальный rollback с повторной загрузкой строки.
- **ORM query-builder guard:** unit-тесты фиксируют все typed predicate-комбинаторы, nullable значения, плоскую композицию, projection/order/pagination call order, Sendable boundary, schema/unmapped-KeyPath ошибки и точный PostgreSQL/SQLite SQL с bind order. Builder не хранит KeyPath или `FieldDescriptor`; отрицательную пагинацию окончательно проверяет dialect renderer.
- **ORM query-execution guard:** unit-тесты фиксируют обязательный SQL execution, DB-order результата, direct last-read-wins refresh, атомарный batch при decode/duplicate-PK error, UoW overlay/commit promotion, body/commit discard и rollback-only после swallowed executor failure. Shared SQLite/live PostgreSQL behavior выполняет typed nullable predicate + ordering + pagination, доказывает явный refresh внешнего UPDATE и видимость eager update/delete/insert через transactional fetch и свежую сессию после commit.
- **ORM query-terminal guard:** `first` фиксирует effective limit, сохранение ordering/offset, пустой limit и direct/UoW snapshot promotion. `count` фиксирует predicate-only semantics, отсутствие identity side effects, ровно одну aggregate row, recoverable result-shape/decode ошибки и rollback-only после executor failure. Shared SQLite/live PostgreSQL behavior проверяет оба terminal-метода до и после transactional update/delete/insert.
- **ORM raw-hydration guard:** unit-тесты фиксируют positional binds, schema validation до SQL, atomic batch, полную unknown-effect invalidation, eviction при direct executor/hydration failure, revision-защиту от позднего in-flight read, очистку прежнего UoW overlay, detached-результат даже для `DELETE ... RETURNING`, запрет transaction-control и rollback-only после post-execution hydration error. Shared SQLite/live PostgreSQL behavior выполняет caller-owned direct/transactional SELECT и доказывает, что eager writes сохраняются в БД даже когда raw fetch консервативно отбрасывает их прежние snapshots.
