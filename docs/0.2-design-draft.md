# PerunORM — дизайн v0.2 (миграции) — РАБОЧИЙ ДРАФТ

> Статус: рабочий дизайн; Slices 1–4 реализованы, следующий delivery slice — 5.
> Prose — RU, код/идентификаторы — EN. Публичный API завершённых slices зафиксирован;
> API последующих slices проходит review перед реализацией.

## 0. Решение и цель

Главная тема 0.2 — **forward-only транзакционные миграции схемы**. Версия 0.1 доказала
DBAL/ORM на PostgreSQL и SQLite, но composition root всё ещё обязан создавать и изменять схему
вручную. 0.2 закрывает этот эксплуатационный пробел, не смешивая его с redesign query/identity
слоя.

Решения верхнего уровня:

- новый additive SwiftPM product `PerunMigrations`;
- существующие `PerunDBAL`, адаптеры и `PerunORM` сохраняют source compatibility;
- порядок массива миграций канонический, применённая история обязана быть его точным префиксом;
- миграция имеет стабильный `id` и явную положительную `revision`;
- весь pending-суффикс применяется **атомарно в одной транзакции**;
- lock удерживается той же транзакцией от чтения истории до commit/rollback;
- PostgreSQL использует один database-wide transaction-scoped advisory lock для всех Perun
  migrators;
- SQLite использует `BEGIN IMMEDIATE`; разные lock keys там намеренно сериализуются сильнее;
- migration body получает ограниченный `MigrationContext`, а не `Database` или голый драйвер;
- transaction-control SQL внутри body запрещён;
- schema diff, introspection, down-migrations и нетранзакционные шаги не входят в 0.2.

JOIN/relations оставлены следующей отдельной темой: они одновременно меняют qualified columns,
aliases, predicates, projections, duplicate-root semantics и identity map. Добавлять их рядом с
операционным lifecycle схемы — два независимых риска в одном minor release.

## 1. Package graph и границы

Новый product содержит один новый публичный target:

```text
PerunMigrations ───────▶ PerunDBAL
                              ▲
                              │ implements capability
PerunDBALPostgres ────────────┤────▶ perun-pgsql
PerunDBALSQLite ──────────────┘────▶ perun-sqlite

PerunORM ──────────────▶ PerunDBAL       (без новой зависимости)
```

`PerunMigrations` не импортит ORM и адаптеры. Он работает через DBAL-порты. Адаптеры не импортят
`PerunMigrations`: новый общий locking capability объявляется в `PerunDBAL`, поэтому циклов нет.

Драйверы остаются неизменными:

- perun-pgsql уже исполняет произвольный SQL внутри scoped transaction;
- perun-sqlite уже принимает `TransactionKind.immediate` в `withTransaction`;
- ни один драйвер не узнаёт о migration plan, tracking table или migration ID.

## 2. Exclusive transaction capability

Обычный `Database.withTransaction` не обещает взаимное исключение между двумя migrator
instances. Нельзя молча считать обычную транзакцию глобальным lock. DBAL получает отдельный
additive capability-протокол; `Database` не приобретает новых requirements.

Proposal:

```swift
public struct DatabaseLockKey: Sendable, Hashable {
    public let rawValue: Int64

    public init(rawValue: Int64)
}

public protocol ExclusiveTransactionDatabase: Database {
    func withExclusiveTransaction<T: Sendable>(
        lockKey: DatabaseLockKey,
        _ body: @Sendable (any Transaction) async throws -> T
    ) async throws -> T
}
```

Контракт: два `withExclusiveTransaction` с одинаковым logical database и `lockKey` не исполняют
body одновременно. Реализация вправе сериализовать больше ключей, но не меньше. Lock всегда
освобождается вместе с commit/rollback и не требует cleanup после crash. Transaction snapshot для
body не закрепляется до успешного получения lock и позволяет увидеть commits предыдущих holders с
тем же key, завершённые до этого момента. Нормальный возврат самого `withExclusiveTransaction`
гарантирует commit; нормальный возврат body лишь запрашивает commit и не исключает post-body
validation error. Ошибка body или cancellation, замеченная до начала commit, означает rollback и
повторный throw. После начала commit outcome может быть неизвестен, как описано в разделе 8, но
известный rollback никогда не возвращается как success. Transaction executor остаётся
closure-scoped; body не передаёт через него transaction-control SQL и не создаёт nested transaction.

Нет default implementation через обычный `withTransaction`: такой fallback компилировался бы,
но нарушал correctness. Custom DBAL adapters поддерживают migrations только после явного
conformance. Эта conformance также подтверждает, что все façade instances одного logical database
координируют одинаковый key, transaction executor отклоняет второй statement до исполнения первого,
а canonical tracking identifiers представляются без truncation или aliases. Paired dialect также
должен поддерживать `createTableHead(ifNotExists: true)` для metadata DDL.

### PostgreSQL

`PostgresDatabase` начинает обычную transaction и до передачи executor caller'у выполняет:

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT pg_advisory_xact_lock($1::bigint)
```

Параметр — стабильный `Int64` key. `pg_advisory_xact_lock` ждёт конкурента и автоматически
освобождается при завершении transaction. `READ COMMITTED` задаётся до первого snapshot-taking
statement, чтобы ожидающая transaction после получения lock увидела commit предыдущего runner даже
при session default `REPEATABLE READ` или `SERIALIZABLE`. Override действует только внутри
exclusive transaction. Server-side `statement_timeout`/cancellation остаётся авторитетным способом
ограничить ожидание. После нормального возврата body adapter выполняет безопасный health probe до
`COMMIT`: проглоченная caller-ом server error оставляет PostgreSQL transaction aborted, поэтому probe
бросает `25P02`, а driver откатывает transaction вместо ложного сообщения об успешном commit.

### SQLite

`SQLiteDatabase` вызывает существующий driver API:

```swift
client.withTransaction(kind: .immediate) { ... }
```

`BEGIN IMMEDIATE` берёт write reservation до чтения migration history. SQLite имеет один writer,
поэтому `lockKey` не различает независимые namespaces — это безопасное over-serialization.
Конкурент ждёт в пределах `SQLiteConfiguration.busyTimeout` (default 5 seconds), затем либо входит
и перечитывает историю, либо получает `SQLITE_BUSY` до migration body. Ни один вариант не допускает
двойное применение. Cancellation, полученная во время ожидания, повторно проверяется после
reservation и приводит к rollback до вызова migration body.

### Lock key

`Migrator` использует один фиксированный versioned namespace `"perun-migrations/v1"` для всего
logical database. Ни tracking table name, ни plan в key не входят. Поэтому два Perun migrators на
одной PostgreSQL database сериализуются даже с разными metadata tables: migration bodies содержат
произвольный DDL, и доказать независимость их ресурсов невозможно.

Нельзя использовать Swift `Hasher`: его seed случайный между процессами. 0.2 фиксирует FNV-1a
64-bit по UTF-8 bytes (offset basis `14695981039346656037`, prime `1099511628211`). Test vector для
namespace выше: unsigned `2311701755587480641`, hex `2014d07fb0704c41`; те же биты передаются как
signed `Int64` без изменения.

Collision с чужим application lock допустим только как лишняя сериализация. Он не может открыть
параллельное исполнение Perun plans. Изменение namespace или алгоритма — protocol change, а не
рефакторинг.

## 3. Migration plan

Минимальная публичная модель:

```swift
public struct Migration: Sendable {
    public let id: String
    public let revision: Int64

    public init(
        id: String,
        revision: Int64 = 1,
        _ apply: @escaping @Sendable (MigrationContext) async throws -> Void
    )
}

public struct Migrator: Sendable {
    public init(
        database: any ExclusiveTransactionDatabase,
        migrations: [Migration],
        trackingTableName: String = "_perun_migrations"
    ) throws

    public func status() async throws -> MigrationStatus
    public func migrate() async throws -> MigrationReport
}
```

Label `trackingTableName` намеренно отличает internal metadata от пользовательских schema tables.
`Migration.init` не бросает: полный plan синхронно валидируется в `Migrator.init` до database I/O.

### ID, revision и порядок

- `id` непустой, уникальный в plan и ограничен стабильным ASCII vocabulary
  `[A-Za-z0-9][A-Za-z0-9._-]{0,127}` (maximum 128 bytes);
- `revision > 0`;
- порядок массива — единственный порядок исполнения, лексическая сортировка ID не применяется;
- applied rows обязаны совпасть с `migrations[0 ..< applied.count]` по position, ID и revision;
- разрешено только дописывать новый suffix;
- удаление, перестановка или изменение revision applied migration — history drift;
- до публикации plan изменение body требует увеличить revision;
- после попадания migration в release или запуска вне ephemeral development её ID, revision и body
  immutable, даже если конкретная database ещё считает её pending;
- closure невозможно честно захешировать, поэтому 0.2 не притворяется, что вычисляет checksum
  автоматически.

Изменять published/applied migration нельзя даже с новой revision: на разных databases она может
иметь разный applied state, а mismatch нужен для раннего отказа. Исправление production-схемы
оформляется новой migration в конце plan.

Tracking table name входит в plan validation и ограничен canonical portable grammar
`[a-z_][a-z0-9_]{0,62}`: lowercase ASCII, maximum 63 bytes. Это исключает backend aliases из-за
case folding или PostgreSQL identifier truncation. Prefix `sqlite_` дополнительно запрещён: SQLite
резервирует его для internal objects. Plan validation (`id`, revision, duplicates, table identifier)
завершается до первого database call. Ошибочный локальный plan не создаёт tracking table и не ждёт
lock.

## 4. Migration context

Migration body не получает `Database`, чтобы не открыть вторую connection и не выйти из общей
transaction. Он также не получает ORM `Session`/`UnitOfWork`: migrations работают ниже ORM.

Proposal:

```swift
public struct MigrationContext: SQLExecutor {
    public var dialect: any SQLDialect { get }
    public var renderer: SQLRenderer { get }
}
```

`execute` остаётся positional и делегирует scoped transaction. Context можно использовать для:

- portable DBAL statements через `SQLRenderer`;
- backend-specific DDL/data backfill через raw SQL;
- параметризованных data migrations.

`MigrationContext.execute` принимает ровно один SQL statement. Второй top-level statement должен
быть обнаружен и отклонён до исполнения первого. Это обязательная часть существующего
`SQLExecutor`/`Transaction` contract и conformance suite для `ExclusiveTransactionDatabase`, а не
случайное свойство built-in drivers. Поэтому `SELECT 1; COMMIT` не может обойти boundary даже у
custom adapter.

До обращения к executor context проверяет, управляет ли первый значимый statement транзакцией:
`BEGIN`, `COMMIT`, `END`, `ROLLBACK`, `ABORT`, `SAVEPOINT`, `RELEASE`, `START TRANSACTION`,
`PREPARE TRANSACTION`, `SET TRANSACTION`. Такой leading command получает
`MigrationExecutionError`; остальные строки передаются transaction executor-у, который атомарно
проверяет single-statement contract. Поэтому trailing control вроде `SELECT 1; COMMIT` не
исполняется и сохраняет исходную driver-specific batch error. Scanner из `Session` переносится в
package-scoped DBAL helper и переиспользуется ORM и migrations; двух security-sensitive tokenizers
не будет.

Каждая migration получает новый context с shared actor-isolated lifecycle:

- `open` принимает одну операцию за раз;
- `closing` запрещает новые операции и ждёт завершения уже начатой;
- `closed` навсегда отклоняет `execute` до обращения к transaction executor.

Сразу после возврата или ошибки body runner вызывает internal `close()`. Если body вернулся при
активной операции, это escaped work: context становится rollback-only, ждёт завершения операции и
заставляет весь batch откатиться. Tracking row вставляется только после успешного `close()`.
Delayed detached task, начавшийся позже, получает `contextClosed` и не достигает database.

Overlapping `execute` в состоянии `open` отклоняется до второго SQL и переводит context в
rollback-only. Порядок migration SQL должен быть виден из последовательного source, а не зависеть
от scheduler. Context нельзя сохранять для последующего использования.

Atomicity распространяется только на transactional database effects, выполненные через context.
Session-scoped state, nontransactional backend effects вроде sequence advancement и необратимые
network/file/other-database side effects в гарантию не входят. Body должен избегать их либо caller
сам обеспечивает idempotency, принимает остаточные effects и определяет recovery.

## 5. Tracking table

Default tracking table: `_perun_migrations`. Имя конфигурируется как один canonical DBAL identifier
по grammar из plan validation, не raw qualified SQL fragment. Schemas/namespaces вне default schema
отложены, пока DBAL не получит структурный qualified identifier.

Все connections одного database pool обязаны разрешать этот unqualified identifier в одну и ту же
physical table. Heterogeneous PostgreSQL `search_path`, SQLite TEMP shadowing или изменение lookup
state из migration body не поддерживаются. Composition root настраивает homogeneous pool, а body
не меняет session lookup state.

Логическая схема:

| Column | Portable type | Contract |
| --- | --- | --- |
| `position` | `int64` | one-based primary key; plan order |
| `id` | `text` | non-null, unique migration ID |
| `revision` | `int64` | non-null positive explicit revision |
| `applied_at` | `timestamp` | non-null UTC commit-attempt timestamp |

Таблица создаётся внутри exclusive transaction после получения lock. Slice 3 сохраняет точный
`SQLCreateTable.init(table:columns:)` и добавляет отдельную explicit-перегрузку
`init(table:columns:ifNotExists:)` без default argument. `SQLDialect` получает requirement
`createTableHead(ifNotExists:) throws` с default implementation: для `false` он возвращает
`CREATE TABLE`, для `true` бросает typed
`SQLDialectFeatureError.createTableIfNotExistsUnsupported`. Это новый error type, а не новый case
существующего public enum. PostgreSQL/SQLite override возвращает
`CREATE TABLE IF NOT EXISTS`.

Default implementation сохраняет source compatibility внешних dialect conformers и не обещает
неуниверсальную grammar. Existing `SQLCreateTable` call sites сохраняют прежний SQL. Compile fixture
с custom dialect и renderer tests входят в Slice 3.

History читается `ORDER BY position`. Каждая запись вставляется после успешного закрытия context
своей migration, но все записи и schema/data effects commit только вместе со всем pending batch.
Tracking table — reserved implementation state: migration body не должен читать или менять её
напрямую. Runner не пытается распознавать table references в произвольном dialect SQL; финальный
metadata snapshot перед commit защищает от persistent row mutation, но не обнаруживает простое
чтение или schema-only изменение вроде нового trigger. Последнее остаётся запрещённым caller
contract, поскольку schema introspection не входит в 0.2.

`applied_at` — audit field, не входящий в drift comparison. Для deterministic unit tests clock
инъектируется внутренним initializer; public API использует system time.

## 6. Алгоритм `migrate()`

1. Синхронно валидировать локальный plan и table name.
2. Вычислить стабильный `DatabaseLockKey`.
3. Войти в `withExclusiveTransaction(lockKey:)`.
4. Создать tracking table `IF NOT EXISTS`.
5. Прочитать applied history и полный initial metadata snapshot в одной consistent transaction.
6. Сверить history с точным plan prefix.
7. Для каждой pending migration последовательно:
   1. создать новый `MigrationContext`;
   2. выполнить body;
   3. закрыть context и дождаться in-flight operation;
   4. только после успешного close вставить tracking row.
8. Если pending suffix был непуст, перечитать полный metadata snapshot.
9. Для непустого suffix проверить, что reread равен initial rows, включая `applied_at`, плюс rows,
   вставленные runner-ом.
10. Проверить cancellation и rollback-only state.
11. Вернуть report caller'у только после успешного commit.

Если pending пуст, transaction остаётся read/check/no-op и сразу commit без лишнего final reread.
Конкурент, ожидавший lock, обязан перечитать history **после** получения lock; pre-lock snapshot
использовать нельзя. Любое изменение, удаление или добавление metadata row из migration body,
сохранившееся к final snapshot, обнаруживается до commit и откатывает весь batch. Net-zero mutation,
полностью восстановленная до reread, неотличима от неизменённого состояния. Metadata schema mutation
запрещена contract-ом, но без introspection не обещается как автоматически обнаруживаемая.

Выбран whole-batch transaction, а не commit-per-migration:

- lock естественно покрывает весь plan на одной connection;
- failure не оставляет половину нового release schema;
- tracking rows и schema effects имеют одну судьбу;
- текущий DBAL не обязан держать connection-scoped lock между несколькими transactions.

Цена — длинная transaction и невозможность PostgreSQL `CREATE INDEX CONCURRENTLY`, SQLite
`VACUUM` и других statements вне transaction. Это осознанный non-goal 0.2; для них позже нужен
отдельный step kind и другой recovery protocol.

## 7. `status()` и reports

`status()` использует тот же exclusive transaction и `CREATE TABLE IF NOT EXISTS`, затем валидирует
history. Поэтому первый `status()` может создать пустую metadata table; он не выполняет user
migrations.

Минимальные данные:

```swift
public struct MigrationReference: Sendable, Hashable {
    public let position: Int64
    public let id: String
    public let revision: Int64
}

public struct MigrationStatus: Sendable, Equatable {
    public let applied: [MigrationReference]
    public let pending: [MigrationReference]
}

public struct MigrationReport: Sendable, Equatable {
    public let applied: [MigrationReference]
}
```

`status.applied` содержит persisted prefix, `status.pending` — локальный suffix. `report.applied`
содержит только migrations, выполненные данным вызовом. Пустой report означает already-current.
Report не обещается при commit error: database history после повторного `status()` — единственный
источник истины.

## 8. Failure, rollback и cancellation

### Error taxonomy

`PerunMigrations` владеет только детерминированными ошибками своего протокола:

- `MigrationPlanError` — invalid ID/revision, duplicate ID или invalid table identifier;
- `MigrationHistoryError` — malformed row, отличие persisted history от exact plan prefix или
  изменение reserved metadata rows из migration body;
- `MigrationExecutionError` — transaction-control escape, overlapping или escaped context
  operation, closed context либо финальный rollback-only state.

Все три типа публичны, `Sendable` и `Equatable`; их payloads не содержат arbitrary underlying
errors. Slice 2 фиксирует plan/history API:

```swift
public enum MigrationPlanError: Error, Sendable, Equatable {
    case invalidMigrationID(position: Int64, id: String)
    case nonPositiveRevision(position: Int64, id: String, revision: Int64)
    case duplicateMigrationID(
        id: String,
        firstPosition: Int64,
        duplicatePosition: Int64
    )
    case invalidTrackingTableName(String)
}

public enum MigrationHistoryError: Error, Sendable, Equatable {
    public enum MalformedRowReason: Sendable, Equatable {
        case unreadable
        case invalidValue
    }

    case malformedRow(
        rowOrdinal: Int64,
        column: String,
        reason: MalformedRowReason
    )
    case nonContiguousPosition(expected: Int64, actual: MigrationReference)
    case unexpectedAppliedMigration(MigrationReference)
    case appliedMigrationMismatch(
        expected: MigrationReference,
        actual: MigrationReference
    )
    case reservedMetadataChanged
}
```

Plan positions и malformed row ordinals — положительные one-based `Int64`; ordinal означает порядок
строки в result, а не значение persisted `position`. `MigrationReference` создаётся библиотекой и
не имеет public initializer. Slice 4 фиксирует точные `MigrationExecutionError` cases:
`contextBusy`, `contextClosed`, `contextOperationEscaped`, `contextRollbackOnly` и
`transactionControlNotAllowed(command:)`.

Connection/acquisition, advisory-lock wait, statement, body и commit errors, которые DBAL возвращает
caller-у, migration layer не заворачивает с потерей backend details. Precedence при rollback failure
остаётся частью `Database.withTransaction` driver contract. Caller может отдельно ловить
driver-specific timeout/contention или single-statement rejection. Если body проглотил statement
error, финальная проверка бросает `MigrationExecutionError` для rollback-only state: исходную
ошибку уже сознательно поглотил body.

### До user SQL

- invalid plan/table name: отказ до database call;
- lock timeout/contention error: ни один migration body не начат;
- malformed/modified history: отказ после lock, до pending body;
- decode/result-shape error metadata table: rollback и отказ.

### Во время body

Любая непойманная ошибка body откатывает весь pending batch. Executor error переводит shared
context state в rollback-only. Если body поймает и проглотит такую ошибку, следующий execute и
финальная проверка всё равно заставят outer transaction бросить и rollback. Это важно для SQLite,
где не каждая statement error автоматически aborts transaction.

Запрещённый transaction-control statement тоже делает context rollback-only: нарушение boundary
нельзя превратить в успешную migration через `catch`.

Runner закрывает context и дожидается in-flight operation также на error path, прежде чем передать
ошибку outer transaction. Поэтому rollback не начинает использовать connection параллельно с
escaped migration SQL.

Чистая локальная ошибка, возникшая до `context.execute` (например, caller validation), находится
под контролем body. Если caller сознательно её поймал и body вернулся нормально, runner не может и
не должен угадывать намерение.

### Cancellation и commit uncertainty

Observed cancellation до commit приводит к rollback через driver contract. Body после rollback
может быть вызван повторно; single-execution guarantee нет. Гарантия 0.2 уже: transactional
schema/data effects, выполненные через context, и tracking rows либо commit вместе один раз, либо
вместе отсутствуют.

Если commit успел на server, но caller получил transport/timeout/cancellation error, outcome может быть
неизвестен. Следующий locked `status()`/`migrate()` устанавливает фактическое database state: при
успешном commit он возвращает no-op, иначе повторно запускает pending body. Внешние side effects в
этот recovery protocol не входят.

## 9. Concurrency contract

Для одного logical database:

- migration bodies любых двух Perun migrators никогда не исполняются одновременно, включая разные
  tracking table names;
- contender читает history только после lock, из snapshot, который позволяет увидеть commit
  предыдущего holder;
- при одинаковых tracking table и plan после commit первого runner второй возвращает no-op;
- при backend lock timeout второй может завершиться исходной driver error до body и безопасно
  повториться;
- crash освобождает transaction-scoped lock через закрытие connection/rollback;
- обычный application SQL advisory lock не соблюдает, поэтому migrations запускаются до начала
  serving traffic или в отдельном maintenance window.

PostgreSQL использует один фиксированный advisory key на database. PostgreSQL advisory locks
database-local, поэтому одинаковый key в другой database не связывает независимые deployments.
SQLite игнорирует key и сериализует writers на уровне database file. Оба backend-а намеренно
over-serialize разные metadata namespaces ради безопасного произвольного DDL.

## 10. Test matrix

### Pure/unit

- empty/invalid/duplicate IDs;
- non-positive revision;
- invalid tracking identifier, включая uppercase, non-ASCII, prefix `sqlite_` и длину больше
  63 bytes;
- applied history exact prefix;
- missing, reordered, inserted-in-middle и revision-mismatch history;
- fixed UTF-8 lock-key vector и независимость key от tracking table name;
- transaction-control scanner с whitespace, semicolons, line/block/nested comments;
- single-statement rejection с trailing transaction control;
- context lifecycle: close, use-after-close, in-flight escape и delayed detached task;
- context rollback-only после swallowed executor error;
- final metadata snapshot detects delete/update/extra row;
- report/status shape и deterministic clock.

### Shared live SQLite + PostgreSQL

Один и тот же suite обязан доказать:

1. fresh database: A+B применены по порядку и записаны;
2. второй run: no-op без повторного body;
3. append C: применяется только C;
4. failure в B: effects и rows всего pending A+B отсутствуют;
5. cancellation: тот же rollback contract;
6. history drift: ни один pending body не стартует;
7. raw data backfill с positional binds;
8. transaction-control замаскирован комментариями и отклонён;
9. `INSERT ...; COMMIT` отклонён до первого statement и не оставляет effect;
10. два concurrent migrators с одной table: один apply, второй no-op либо lock-timeout до body;
11. два migrators с разными tables не выполняют bodies одновременно;
12. escaped in-flight context и mutation tracking rows откатывают весь batch;
13. shutdown/reopen: status восстанавливается только из tracking table.

SQLite contention case использует отдельный временный file-backed database, pool минимум из двух
connections и явный busy timeout. Private `:memory:` database не доказывает межconnection lock.

Backend-specific tests отдельно фиксируют:

- PostgreSQL advisory lock SQL, bind type/cast, release после commit/rollback, fresh snapshot после
  ожидания при session default `REPEATABLE READ` и отказ от false-success для aborted transaction;
- SQLite `BEGIN IMMEDIATE`, busy timeout, cancellation до body, отсутствие pre-lock read и
  видимость commit holder;
- single-statement execution path не допускает SQL batch ни с пустыми, ни с непустыми binds;
- exact portable DDL tracking table на обоих dialects.
